# Bilingual QA — 경계면 교차 검증

## 개별 정상, 연결 파탄

이 종류의 프로젝트에서 가장 흔한 실패는 파일 하나가 잘못되는 것이 아니다. **모든 파일이 개별적으로 정상인데 연결 지점에서 어긋나는 것**이다. 카피 파일에 12개 씬이 있고 디자인 스펙에 12개 씬이 있어도, ID 하나가 어긋나면 화면에는 11개만 뜬다. 각각을 따로 열어보면 아무 문제가 없다.

따라서 검증의 단위는 파일이 아니라 **경계면**이다. 항상 양쪽을 동시에 열어 대조한다.

## 검증 원칙

**"존재하는가"가 아니라 "일치하는가"를 묻는다.** 이 차이가 QA의 전부다.

| 약한 질문 | 강한 질문 |
|----------|----------|
| 씬 데이터 파일이 있는가 | 네 산출물의 씬 ID 집합이 완전히 동일한가 |
| 이미지 경로가 적혀 있는가 | 그 경로의 파일이 디스크에 실제로 있는가 |
| 번역문이 있는가 | 두 언어가 같은 내용을 말하는가 |
| 폰트를 지정했는가 | 그 폰트가 해당 글리프를 실제로 포함하는가 |

**의심스러우면 실물을 확인한다.** JSON에 적힌 것을 믿지 않는다. `ls`로 파일을 보고, 크기를 재고, 실제 문자열을 grep한다. 서류상 통과가 아니라 실물 통과를 확인한다.

**점진적으로 검수한다.** 전부 완성된 뒤 한 번에 보면, 발견된 구조적 결함을 고칠 시간이 없다. 골격 시점·중간 시점·완성 시점에 각각 본다.

## 교차 검증 절차

### 1. 씬 ID 정합성

모든 산출물에서 ID 집합을 뽑아 차집합을 계산한다. 눈으로 세지 않는다.

```bash
for f in _workspace/01_*timeline.json _workspace/03_*bilingual.json \
         _workspace/04_*scenes.json data/scenes.js; do
  echo "== $f"; grep -o '"id"[[:space:]]*:[[:space:]]*"[^"]*"' "$f" 2>/dev/null \
    | sed 's/.*"\([^"]*\)"$/\1/' | sort
done
```

한쪽에만 있는 ID가 진짜 결함이다. 개수가 같아도 안심하지 않는다 — 개수가 같으면서 내용이 어긋난 경우가 발견하기 가장 어렵다.

### 2. 미디어 참조 ↔ 실제 파일

```bash
grep -o '"src"[[:space:]]*:[[:space:]]*"[^"]*"' data/scenes.js \
  | sed 's/.*"\([^"]*\)"$/\1/' | sort -u | while read -r p; do
  [ -f "$p" ] && printf 'OK   %8s  %s\n' "$(du -k "$p" | cut -f1)K" "$p" \
                || printf 'MISS           %s\n' "$p"
done
```

`MISS`는 화면에 깨진 이미지 아이콘으로 나타난다. 선물이 망가져 보이는 가장 빠른 길이다.

### 3. 글리프·인코딩 무결성

원문 언어의 특수 문자가 실제 파일에 살아 있는지 확인한다. 몽골어라면 `Ө ө Ү ү`가 핵심이다.

```bash
grep -c 'Ө\|ө\|Ү\|ү' data/scenes.js
file -i data/scenes.js      # charset=utf-8 이어야 한다
grep -c 'charset="utf-8"\|lang="mn"' index.html
```

폰트가 해당 글리프를 포함하는지는 **선언이 아니라 실제 렌더링**으로 확인한다. 웹폰트 URL의 서브셋 파라미터에 `cyrillic-ext`가 포함되어 있는지 본다.

### 4. 언어 간 의미 대응 — 가장 중요

의뢰인이 A언어로만 검수하고 승인하는데, 수신자는 B언어만 읽는다면, **두 언어가 다른 말을 하고 있어도 아무도 모른다.** 이것이 이 QA의 존재 이유다.

씬별로 두 언어를 나란히 놓고 확인한다:
- B언어에만 있는 문장 (의뢰인이 승인하지 않은 내용)
- A언어에만 있는 문장 (의뢰인이 승인했지만 전달되지 않는 내용)
- 어감이 크게 다른 문장 (특히 사과·약속 등 무게가 실린 부분)
- 고유명사·날짜·이름의 불일치

발견된 것은 전부 보고한다. "의도적 의역일 수 있다"고 판단해 넘기지 않는다. 판단은 의뢰인이 한다.

### 5. 사실 검증

날짜·이름은 원본 브리프와 직접 대조한다. 생일이 하루 틀린 축하 페이지는 다른 모든 완성도를 무의미하게 만든다. 씬 배열이 시간 오름차순인지도 확인한다.

### 6. 성능·반응형·접근성

- 이미지: 장당 400KB 이하, 전체 5MB 이하
- 첫 화면 외 `loading="lazy"`, `width`/`height` 명시
- 375px에서 가로 스크롤 발생 → 결함
- 애니메이션이 `transform`/`opacity` 외 속성 사용 → 결함
- `prefers-reduced-motion` 대응 존재
- 오디오 자동재생 시도 없음, 음소거 상시 노출, 파일 부재 시 버튼 숨김
- 절대 경로(`/assets/`) 사용 → 하위 경로 배포에서 404
- `.nojekyll`, OG 태그(`og:image`는 절대 URL) 존재
- 이미지 `alt` 속성 존재

## 결함 보고

심각도 3단계. **차단** 등급은 보고서에만 적지 않고 담당자에게 즉시 알린다.

| 등급 | 기준 | 예 |
|------|------|-----|
| 차단 | 이대로 전달하면 안 됨 | 글리프 깨짐, 날짜 오류, 이미지 전부 누락, 언어 간 내용 불일치 |
| 중요 | 품질을 눈에 띄게 해침 | 5MB 초과, 모바일 가로 스크롤, OG 태그 누락 |
| 개선 | 있으면 더 좋음 | 미세한 정렬, 여백 |

결함은 **재현 방법과 함께** 전달한다. "레이아웃이 이상함"은 고칠 수 없다. "375px에서 S07 헤드라인이 가로 스크롤을 만듦"은 고칠 수 있다.

## 의뢰인용 검수 대조표

의뢰인이 이것만 보고 승인/반려할 수 있어야 한다. 씬마다:

```markdown
## S04 · 2022-05-05 · 첫아이 탄생

| | 내용 |
|---|---|
| 화면에 뜨는 실제 문구 | (원문 그대로) |
| 그 문구의 정확한 뜻 | (직역에 가깝게. 예쁘게 다듬지 않는다) |
| 사용된 기법 | 두운 Бү-Бү / 없음 |
| 사진 | assets/img/2022-01.jpg — 있음 |
| 확인 필요 | 이 표현이 의도와 맞는지 확인 요청 |
```

뜻풀이를 예쁘게 다듬으면 검수가 무의미해진다. 의뢰인은 **실제로 무엇이 쓰였는지**를 알아야 한다.

## 재검증 한계

생성-검증 루프는 최대 3회로 제한한다. 무한히 도는 것보다, 남은 결함을 의뢰인에게 정직하게 보고하고 판단을 넘기는 편이 낫다. 이전 결함이 실제로 고쳐졌는지 먼저 확인한 뒤 신규 결함을 찾는다 — 고쳤다고 보고된 항목이 그대로인 경우가 드물지 않다.
